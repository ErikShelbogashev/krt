## Вопросы владельцу

**Q1. Раскладка пакетов.**
- (а) по вики: `krt.app.<фича>` (порты-Composable, операции), `krt.domain.{scene, render, camera}`, `krt.i9ns.objfile`, `krt.infra` (корень композиции), `krt.platform` (математика `Point3`, утилиты AWT);
- (б) как в Trainer Advisor: то же, но `core` вместо `domain` и `tech` вместо `platform`.
- Рекомендация: **(а)**, вики первоисточник, а `core`/`tech` — локальные имена автора в одном проекте. Деление `app` по фичам UI: `camera`, `scene`, `render`, `settings`.

**Q2. Случайность в трансформациях.**
- (а) передавать `Random` параметром во все вычисления (`ray`, `scatter`, генерация сцены, перемешивание пикселей); рендерер создаёт по экземпляру на поток с seed от операции. Даёт детерминированные golden-тесты.
- (б) оставить глобальный `Random` и записать в ADR как осознанное отличие (Монте-Карло, производительность).
- Рекомендация: **(а)**. Без неё нет тестов (A1). Издержки: лишний параметр в горячем пути, на производительность влияет слабо. У автора: время/случайность приходят параметрами (`pure-functions.adoc`).

**Q3. Что считать портом в Compose.**
- (а) порт — обработчик события (лямбда `onClick`/`onValueChange`/`onDrag`), он вызывает одну операцию; Composable-функции — это представление, их вложенность портом→портом не считается.
- (б) порт — Composable-панель целиком.
- Рекомендация: **(а)**: точнее соответствует определению «точка входа» и правилу «метод порта — один вызов».

**Q4. Как запускать перерисовку.**
- (а) явно: каждая операция «изменить X» заканчивается вызовом доменной операции `render(...)` (как сейчас, но вынесено из портов);
- (б) реактивно: операции только меняют состояние, рендерер подписан на изменения ресурсов.
- Рекомендация: **(а)** для этого рефакторинга: поведение не меняется и поток управления остаётся явным (`ergo-code-imperatives.adoc` «Сохраняй в самом действии явный поток управления»). (б) — отдельное изменение поведения.

**Q5. Неизменяемая модель.** Сделать `Point3` и объекты сцены неизменяемыми (`val`, `translate` возвращает копию), сцена — ресурс с изменяемой ссылкой на неизменяемый список. Рекомендация: **да**; операторы `Point3` уже создают новые объекты, аллокаций почти не прибавится. Закрывает и гонку данных D4.

**Q6. DI и корень композиции.** Spring нет. Рекомендация: ручной корень композиции в `krt.infra` (создание ресурсов и операций в `main`), без DI-фреймворка (`ergo-arch.adoc`: блоки «создаются и связываются DI-контейнером», но KISS-оговорка допускает ручную сборку).

**Q7. Тесты.** Рекомендация: JUnit 5 + (после Q2) golden-тест кадра с фиксированным seed и малым разрешением; тесты операций через их публичный API без моков; Compose UI-тесты не добавлять на этом этапе. Лимиты вики: тест ≤10 с, набор ≤300 с (`testing/principles/fast-tests.adoc`).

**Q8. Пороги.** Оставить как в вики: связи ≤4 желательно / ≤8 строго, порт ≤1, действие ≤4, трансформация ≤15. Рекомендация: **как в вики**, без ADR.

**Q9. Дефекты из раздела I.** Рекомендация: не трогать в ходе рефакторинга; после него — отдельные PR с изменением поведения, по одному на дефект. Исключение — закрытие пула при выходе (E), его можно сделать первым маленьким PR.
